# 项目评审与改进建议

- 评审日期：2026-11-06
- 评审范围：`radar/core`、`radar/sources/hongguo`、`radar/analysis/*`、`radar/site.py`、`web/js`、GitHub 工作流与测试
- 验证情况：`python3 -m unittest discover -s tests -t .` 共 22 个测试全部通过；`analysis.disabled` 的行为已实测确认
- 数据现状：快照约 315 KB/天（723 部剧、4 个榜各 100 条），目录 995 部剧、约 1.0 MB

## 总体评价

四层结构（Source 产出统一快照 → Analyzer 纯计算 → Reporter/View 消费）划分得干净：

- 插件注册表 + `depends` 拓扑排序，新增数据源/分析器/报告器不用改主流程；
- 快照只追加不改写，原子写入，便于回溯和重算；
- HTTP 层如实标明 UA、全局限速、重试退避；
- 只用标准库，部署和本地运行成本都很低。

主要问题不在架构方向，而在**几个配置项与工作流逻辑没有真正闭环**，以及**数据量增长后的存储/加载方式**。

## 一、确定的逻辑缺陷（建议优先修）

### 1. `analysis.disabled` 对大多数分析器不生效

**位置**：`radar/analysis/runner.py:59-61`、`radar/analysis/runner.py:37-52`

先从名单里剔除 disabled，但 `_order()` 的 `visit()`（`runner.py:48`）会无条件递归访问 `depends`。实测把 `tags` 设为 disabled，运行顺序里仍然出现 `tags`（因为 `exports`、`insights` 依赖它）。

也就是说，凡是「被其他启用分析器依赖」的分析器都关不掉，而内置分析器几乎全部如此。

**建议**：二选一——

- (a) 配置里禁用了一个仍被依赖的分析器时直接报错，提示修改依赖；
- (b) 级联禁用依赖它的分析器并打日志。

不要静默忽略。

### 2. 一次部署失败，看板可能陈旧一整天

**位置**：`.github/workflows/radar.yml:65-71`、`.github/workflows/radar.yml:98`

`Decide` 只有在 `new_snapshot=true` 时才发布。当天 10:25 采集成功、commit 成功，但 deploy job 失败后，后续 11:40 / 14:10 / 17:00 / 21:00 的 `collect` 都返回 `exists`，`new_snapshot=false`，于是**当天再也不会重新部署**，直到第二天有新快照。这属于静默故障。

**建议**：

- 在仓库里提交一个轻量的「已发布批次」标记（deploy 成功后由另一个带 `contents: write` 的 job 写入）；或
- 退一步：定时任务里只要「今天的快照已存在」就 build + deploy。Pages 部署很便宜，代价是每天多部署几次。

### 3. `metrics` 的「上一期」可能选到 stale 快照

**位置**：`radar/analysis/metrics.py:61`、`radar/analysis/history.py:30`

`metrics` 用 `h.previous()`，它会返回包含 `stale=true` 的快照；而名次变化走的是 `History.fresh`（过滤 stale）。手动 `--allow-stale` 之后，同一份 `metrics.json` 里会出现两套基准日：名次按「上一个榜单日」比较，收藏/热度增量按「上一份快照」且除以不同的 `gap`。

**建议**：统一按 `fresh` 取上一期，或至少在 `prev_date` / `gap` 上明确口径。

### 4. 掉榜标记 `removed_on` 不会复位

**位置**：`radar/sources/hongguo/source.py:93`、`radar/sources/hongguo/source.py:240`

`_update_catalog` 在该剧重新出现时不会清除 `removed_on`；之后它一旦掉榜就永久不再被追踪。

**建议**：在 `_update_catalog` 里见到该 id 时 `entry.pop("removed_on", None)`。

### 5. 观察列表的失败结果永久缓存

**位置**：`radar/sources/hongguo/source.py:191`、`radar/sources/hongguo/source.py:198`

只复用 `status == "ok"` 的缓存，但 `not_found` / `ambiguous` 写进缓存后永远不会重试。剧可能后来才上线/改名。

**建议**：给负缓存加 TTL（比如 7 天）。

### 6. 404 判定依赖异常文本

**位置**：`radar/sources/hongguo/source.py:220`

用 `"HTTP 404" in str(exc)` 判断下架。建议让 `FetchError` 携带 `status` 字段（`core/http.py` 里已经有 status），用 `exc.status == 404`，避免 URL 内容或未来改文案导致误判。

## 二、健壮性与安全

- **CSV 注入**：`radar/analysis/exports.py:18` 原样写出第三方简介/标题。若内容以 `= + - @` 开头，Excel/飞书打开时可能当公式执行。建议对这类单元格加 `'` 前缀（或统一转义）。
- **`build --out` 误删风险**：`radar/site.py:69` 对 `out` 直接 `shutil.rmtree`。如果误传 `--out .` 会删掉仓库。建议校验 `out` 不是项目根目录及其祖先、不是 `/`。
- **详情页未校验 id**：`parse_detail_page` 返回页面自己的 `series_id`，`source.py` 却按请求的 id 存。建议加一行 `if details[sid]["id"] != sid: 记为错误`，防止跳转/占位页污染数据。
- **配置无校验**：未知的 `boards` 被静默丢弃（`source.py:44`）、`potential_weights` 的未知键被静默忽略、负数天数/上限没有检查。建议在 `load_config` 后加一个 `validate()`，启动即失败。
- **stale 判断可更可靠**：`source.py:_same_boards` 只比榜单条目；可以优先比较页面上的 `label_date`（`parse_rank_page` 已解析），日期前进了就一定是新数据，再辅以条目对比。
- **前端 CDN 依赖**：`web/index.html` 从 jsDelivr 加载 ECharts、从 Google Fonts 加载字体，没有 SRI。网络异常时图表会降级（`charts.js` 已处理），但建议自托管 ECharts 或至少加 `integrity`，同时改善国内访问体验。

## 三、随数据增长会暴露的规模问题

### 1. 快照体积

现在每天约 315 KB，`history_window_days=400` 意味着每次 build 要把 **~126 MB 原始 JSON** 全部读进内存解析；git 每年新增约 115 MB。实测 gzip 后是 **63 KB（约 5 倍压缩）**。

**建议**：快照落盘改为 `.json.gz`（`Store` 里统一读写，分析层几乎不用改），或按月归档 + 索引。这是投入小、收益最大的一项。

### 2. `History` 无索引

`dramas` 分析器对每部剧调 `h.series()`（`history.py:90`），内部遍历全部快照，复杂度 O(剧数 × 天数)；同时每部剧写一个 JSON 文件。现在 995 部 × 24 天没问题，长期会变慢。

**建议**：在 `History` 里一次性建 `points_by_id` 索引（单遍扫描），`series()` 直接查。

### 3. `catalog` 每天整文件重写

1 MB、约 1000 条，git diff 每天几千行。可考虑 `compact=True` 写入（牺牲可读性换体积），或改为按 `last_seen` 分区，但优先级低于快照 gzip。

## 四、前端逻辑

- **路由竞态**：`web/js/app.js:75-90` 在 `await def.render()` 之后直接往 `root` 追加内容。用户快速切换页面时，旧页面的异步渲染可能追加到新页面里。建议加一个自增 `renderToken`，await 后校验 token 再渲染（`drama.js` 已有类似 `current !== id` 的保护）。
- **静态资源缓存失效不完整**：`radar/site.py:62` 只给 `css/style.css` 和 `js/app.js` 加了 `?v=`，但 `app.js` 里 `import` 的所有 ES module（`views/*`、`lib/*`）URL 不变，部署后浏览器可能继续用旧模块。建议 build 时给所有 `import ... from "./xxx.js"` 追加版本参数，或用 import map + 统一版本。
- **潜力页「分组对比」丢 `unknown` 类型**：`web/js/views/potential.js` 的 `KINDS` 只有 real/ai/comic，而 `kind` 可能为 `unknown`（只在热播榜、不在任何分类榜的剧），分组模式下这些候选会消失但计数仍算在「全部」里。建议补一个「其他」分组或明确过滤。

## 五、测试、CI 与文档

- 测试覆盖核心解析/采集/分析，但没有覆盖：`Fetcher` 的重试与限速、`_order` / disabled 行为、原子写、CSV 转义、stale 快照对分析的影响。修上面的 P0 时顺手补测试，成本很低。
- CI 目前只跑单测，没有 lint/类型检查。可以加 `ruff`（只做开发期检查，不影响「运行时零依赖」的承诺）和 `python -m compileall`。
- 文档与实现不符：
  - `docs/EXTENDING.md` 说 `analysis.disabled = [...]` 能关掉分析器（见缺陷 1）；
  - 「看板页面都是插件，注册即可」——实际上新页面必须手动改 `web/js/views/index.js`。修代码后建议一并更新。

## 六、架构层面（可选，不急）

同一个快照字段名在 `source.py`、`metrics.py`、`exports.py`、`docs/DATA.md`、前端 view 里各写一遍（如 `review_count`），任何一处拼错都会静默变成 `None`。

**建议**：加一个 `radar/core/schema.py`，集中定义字段集合 + `validate_snapshot()`，在 `Store.save/load` 时校验。这样数据契约就有单一事实来源，也方便以后加 `SCHEMA_VERSION` 迁移。

类似地，`Context.results` 是纯字符串 key，`insights` 直接取 6 个结果，缺少依赖时只会在运行时 `KeyError`——可以考虑显式的 `require(ctx, "metrics")`。

## 建议动手顺序

1. `disabled` 真正生效（逻辑缺陷，影响配置可信度）
2. 部署失败自愈（运维可靠性）
3. `metrics` 统一 fresh 基准
4. 快照 gzip（长期成本，改动集中在 `Store`）
5. CSV 转义 + `--out` 保护 + 404 类型化（小改动、防事故）
6. 前端路由 token 与模块缓存版本
